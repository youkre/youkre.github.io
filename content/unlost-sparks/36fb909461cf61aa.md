任何解析器中最核心的就是游标管理。Goldmark 中的游标管理及比较奇怪，或者说混乱。

## Reader 中的行与字符移动

我们研究一下 Goldmark 到底是怎么管理游标的，其中最重要的一个类型是：

```go
type Segment struct {
	Start int
	Stop int
	Padding int
	ForceNewline bool
}
```

在 Goldmark 的代码中，`Segment` 往往用来表示某一行的位置，但是它并不专门用来表示行的起始位置的。它也经常被用来表示一行中的某一小段。实际上 Goldmark 在用 Start 字段表示当前游标指向的字符位置，所以这个字段就是解析器中常用的游标。

`Padding` 这个字段用法比较别扭，也是大部分问题的来源，后面再分析。

基于行的移动不可能忽略行首位置，在 `Reader` 的实现中，有 `head` 这个字段，用来表示当前行的行首位置的，从下面的用法可以看出来：

```go
type reader struct {
	source       []byte
	sourceLength int
	line         int
	peekedLine   []byte
	pos          Segment
	head         int
	lineOffset   int
}

func (r *reader) AdvanceLine() {
	r.lineOffset = -1
	r.peekedLine = nil
	r.pos.Start = r.pos.Stop
	r.head = r.pos.Start
	if r.pos.Start < 0 || r.pos.Start >= r.sourceLength {
		return
	}
	r.pos.Stop = r.sourceLength
	i := 0
	if r.source[r.pos.Start] != '\n' {
		i = bytes.IndexByte(r.source[r.pos.Start:], '\n')
	}
	if i != -1 {
		r.pos.Stop = r.pos.Start + i + 1
	}
	r.line++
	r.pos.Padding = 0
}

func (r *reader) Advance(n int) {
	r.lineOffset = -1
	if n < len(r.peekedLine) && r.pos.Padding == 0 {
		r.pos.Start += n
		r.peekedLine = nil
		return
	}
	r.peekedLine = nil
	l := r.sourceLength
	for ; n > 0 && r.pos.Start < l; n-- {
		if r.pos.Padding != 0 {
			r.pos.Padding--
			continue
		}
		if r.source[r.pos.Start] == '\n' {
			r.AdvanceLine()
			continue
		}
		r.pos.Start++
	}
}
```

这就带来了变量管理的问题：可变量与不变量分散在不同位置。`Segment` 一部分是可变的，而 `reader` 中的 `head` 又发挥了行首锚点的作用。

我认为应该针对行的的位置，应该定义一个表示首尾位置的不变类型：

```python
@dataclass(frozen=True, slots=True)
class LineContext:
    start: int
    end: int
    cols: List[int] = field(default_factory=list)

class Reader:
    def __init__(self, src: str):
        src = src.replace('\r\n', '\n')
        if src and src[-1] != '\n':
            src += '\n'
        
        self._src: str = src
        self._length: int = len(src)

        # current line number.
        # Start from -1 so first line is 0.
        self._line_num: int = -1  
        self._line_ctx: LineContext = LineContext(
            start=0,
            end=0
        )

        self._next_line_start: int = 0 # next line start offset
        self._cursor: int = 0 # next char offset
```

那么 `AdvanceLine` 可以这样实现：

```python
def advance_line(self) -> LineContext | None:
    if self._length == 0:
        return None

    if self._next_line_start >= self._length:
        self._next_line_start += 1 # Is this needed? Might not. Anyway, it's safe guard.
        return None

    next_end = self._src.find('\n', self._next_line_start)
    if next_end == -1:  # Passed EOF?
        return None

    start_idx = self._next_line_start
    stop_idx = next_end + 1
    cols = self.map_char_to_col(start_idx, stop_idx)
    
    self._line_ctx = LineContext(
        start=self._next_line_start,
        end=next_end + 1,
        cols=cols,
    )

    # global char cursor positioned to current line start.
    self._cursor = self._line_ctx.start

    # position of next line start.
    self._next_line_start = next_end + 1 
    self._line_num += 1 # increase line number.

    return self._line_ctx
```

## 列宽与 tab

我们没有解释 Segment.Padding 的含义。要理解它的用途，需要理解 tab 到底表示什么。先看下这个函数：

```go
func TabWidth(currentPos int) int {
	return 4 - currentPos%4
}

func (r *reader) LineOffset() int {
	if r.lineOffset < 0 {
		v := 0
		for i := r.head; i < r.pos.Start; i++ {
			if r.source[i] == '\t' {
				v += util.TabWidth(v)
			} else {
				v++
			}
		}
		r.lineOffset = v - r.pos.Padding
	}
	return r.lineOffset
}
```

它在算从物理行首 (`head`) 到当前消费位置 (`pos.Start`) 之间，一共占据了多少个可视字符宽度。

假设把屏幕按照一个空格划成一个列，4 个列为一个网格单元，一个 tab 可能跨越 4 列、3 列、2 列、列，取决于你在这个网格中那个位置按下 tab 键，tab 的结尾始终对齐到这个网格的末尾。那么 `v` 统计的是按照空格划分的列数，也就是从 `head` 行首到当前片段起始位置所在列，到底跨越了多少列。

这里“当前片段所在列”的含义，并不是指 `Start` 这个变量所指向的位置，因为这个变量本质上是字符的索引位置，由于一个 tab 可能跨越多列，当前片段应该开始的列，和 `Start` 字符所在的列，可能并不一致，例如，片段开始的位置处于 tab 一半的位置，但是你不可能跳过半个字符，所以要把整个 tab 跳过去，但是这就比实际需要的列多了，`padding` 补足字符跳跃一个 tab 时多跨越的列数。

因此，`LineOffset` 表达的是当前字符所在位置距离行首跨越了多少个列，这个值仅限于当前行内，更确切的名字可能是 `ColumnOffset`

为了避免重复计算，Goldmark 在 `reader` 这个结构体中用 `lineOffset` 缓存了每次计算的值：

```go
type reader struct {
	source       []byte
	sourceLength int
	line         int
	peekedLine   []byte
	pos          Segment
	head         int
	lineOffset   int
}
```

如果 `lineOffset` 不是 -1，`LineOffset()` 就返回已经计算好的值，否则就重新计算。这虽然避免了重复计算当前片段跨越的列数，但是依然会导致重复计算，想一下，为什么？

`lineOffset` 这个变量缓存的，始终是当前这个片段窗口静止时，距离行首有多少个列。一旦这个窗口移动了，就要重新计算，因为每次跳过若干字符时，都需要从行首开始重新数目前该行跳过的字符中有多少个 tab，这些 tab 实际所占的列累积起来到底是相当于多少个空格列。因此，我们会看到，凡是移动游标的地方，都重置缓存变量 `lineOffset`：

```go
func (r *reader) Advance(n int) {
	r.lineOffset = -1
    // 略
}

func (r *reader) AdvanceToEOL() {
	if r.pos.Start >= r.sourceLength {
		return
	}

	r.lineOffset = -1
    // 略
}

func (r *reader) AdvanceLine() {
	r.lineOffset = -1
    // 略
}

func (r *reader) SetPosition(line int, pos Segment) {
	r.lineOffset = -1
	// 略
}

func (r *reader) ResetPosition() {
	r.line = -1
	// 略
}
```

对于 markdown 解析来说，重复计算其实不是一个很大的问题，因为通常基于行的解析每行行首都有某些特征，所以通常计算前几个字符，后面就可以不再需要计算 LineOffset 了。但是如果一行中的每个字符都需要处理一下呢？每个字符都运行一次 LineOffset 似乎就不太能接受了，那就最好 `expandtabs(4)`，或者换个思路，把每个字符对应的列号记下来怎么样？每次移动到一行时循环一遍就行了。这就是前面 `LineContext` 中 `cols` 的用途：

```python
class Line(NamedTuple):
    start: int
    stop: int
    cols: List[int]

def calc_tab_width(current_column: int) -> int:
    return 4 - (current_column % 4)

class Reader:
    def map_char_to_col(self, start: int, stop: int) -> List[int]:
        char_count = stop - start
        # We need to collect N+1 Viewport Boundaries
        char_cols = [-1] * (char_count + 1)

        col_n = 0 # First column always starts from 0. 
        for char_idx in range(char_count): # char_idx is relative to start
            char_cols[char_idx] = col_n
            ch = self._src[start+char_idx]
            # Clalculate next column based on
            # current char's column
            if ch == '\t':
                col_n += calc_tab_width(col_n)
            else:
                col_n += 1

        char_cols[char_count] = col_n # total columns, the last post.

        return char_cols
```
